# Known issues

Symptom first, then the root cause in the code, then what to do. Add an entry when you find a problem you cannot fix right away; remove it in the commit that fixes it.

| # | Symptom | Root cause | Where | Status / next step |
|---|---|---|---|---|
| 1 | Agentic answers use little of what the agent found; more MCP research barely changes the answer | Only the agent's evidence ids reach the pipeline, capped at `HARNESS_AGENTIC_MAX_MCP_SEEDS` (6, one per paper first). Its findings and summary are dropped, and the pipeline repeats retrieval and extraction. | `harness_agent/research.py` (`_select_seeds`, `_run_shared_pipeline`) | Addressed in Phase 3b/3d (`HARNESS_AGENT_HANDOFF=findings`, paper readers): findings with evidence ids reach the pipeline as seeds and notes. Seeds are capped at 12 (was 6) since the Phase 4 slice 4 change; measure on gold whether it helps. |
| 2 | `verified_claim_ids` is always empty | The agent runs before the pipeline, so there are no preliminary claims to confirm (`_grounded_context(None, ...)`). | `harness_agent/research.py` | Still by design. Claim-level verdicts now come from the answer verifier instead: `readings[].answerSentences` (accepted / removed / from_facts, with sources and reasons). |
| 3 | Some concept readings show "0 corpus passages" | Concepts are proposed first and grounded afterwards; grounding searches each LLM search term as an exact quoted phrase, and multi-word phrases rarely match. Ungrounded concepts are still shown to reach the minimum of 3. | `harness_agent/concepts.py` (`_ground_ranked`) | Addressed in Phase 3a (`HARNESS_CONCEPT_GROUNDING=retrieve_first`): passages are retrieved first, readings cite them, and ungrounded readings are hidden unless none has support. `legacy` restores the old order. |
| 4 | Heavy keeps working after a run is stopped or times out; later runs are slow | A stopped run abandons its model call, but a non-streaming request cannot be cancelled: in LiteLLM 1.102 only streaming requests react to a client disconnect, so the upstream vLLM generation runs to the end. | `harness_extraction/call_control.py`, `model_client.py` | Set `HARNESS_MODEL_STREAM=true`: the client then closes the stream on Stop and LiteLLM/vLLM abort the generation. Verify on the node (watch `running` in `/v1/status` drop after Stop), then make it the default. The agent tool loop (`mcp.py`) is not streamed yet. |
| 5 | Heavy is overloaded when the agent runs on Lite | The heavy-busy deferral only applies when the agent model is the high model; with Lite as agent, only `HARNESS_MAX_CONCURRENT_HEAVY` bounds Heavy. | `harness_agent/research.py` (`_check_heavy_load`) | Decide in phase 3 whether pipeline Heavy calls should wait on `/v1/status`. |
| 6 | Heavy latency spikes under parallel runs | Heavy's KV cache held about 69k tokens (2.1 full 32k requests) with the model dtype; long requests beyond that are preempted. | thesis-llm-setup `profiles/a100-3x40.yaml` | FP8 KV cache enabled on Heavy (restart required). Check `preemptions` in `/v1/status`; load test before raising limits. |
| 7 | The `extraction/triple_extraction` prompt has no effect on live runs | The API builds every runner with `edc=True`, so extraction always uses the EDC prompts; `extract()` runs only when `edc=False`. | `api/runtime.py` (`_runner`), `harness_baseline/research_steps.py` | Keep the prompt for the non-EDC mode; do not tune it expecting live changes. |
| 8 | Precision/recall panel ("Interpretation") is empty | No approved gold rows for the questions yet. The scorer (strict / entailed / soft, vital recall, judged precision, complexity × path) and `make evaluate` are in place. | `labelling`, `harness_evaluation`, `api/routes_benchmark.py` | Phase 2: first gold batch; the UI panel still has to show the new fields. |
| 9 | Gold scoring penalises correct claims with invented predicates | Gold uses DBLP vocabulary only; the live system may invent `hrn:` predicates. | `harness_evaluation`, `labelling` | Mitigated: DBLP predicates are scored locally closed, invented ones via the entailed level (`datasets/ontology/predicate_relations.ttl`) and judged precision. Since Phase 4 every invented property has a parent in the run's `subschema.ttl`, but the scorer does not read run subschemas yet, so those parents do not credit anything; the content core (next slice) will give invented properties shared, scorable parents. |
| 10 | Structured replies sometimes fail to parse | Calls request `response_format: json_object`, which does not enforce the schema. | `harness_extraction/model_client.py` | Candidate: vLLM structured outputs with `json_schema` from the Pydantic models; measure on gold first. |
| 11 | Hybrid retrieval changes nothing | No dense index for the current `passages.jsonl` (missing, or stale after re-ingest), the embedding model is down, or it now returns a different dimension; ranking silently falls back to BM25: the hybrid round in `retrieval.json` (`queries[].retrieval`) reads `bm25` instead of `bm25+dense`. | `harness_corpus/dense.py`, `store.py` | Run `make embed` after every ingest; check the API log for "Dense index … rebuild". Dense retrieval is used only with `HARNESS_RETRIEVAL_MODE=hybrid`. |
| 12 | Research answers are thin (median 3 fact edges; 15 of 34 have 1-2; Phase 4 batch: median 2.5 extracted) | Measured with `make graph-shape`. Only up to `HARNESS_AGENTIC_MAX_PASSAGES` passages reached extraction, of which `HARNESS_AGENTIC_MAX_MCP_SEEDS` came from the agent, and EDC batches of 2 passages ran one after the other, so more passages cost linear time. | `harness_baseline/research_steps.py` (`_extract_build`), `retrieval.py`, `harness_agent/research.py` (`_select_seeds`) | Batches now run in parallel (`HARNESS_EXTRACTION_CONCURRENCY`, 3), caps raised to 24 passages / 12 seeds, named papers get an even share. Rerun the 30 questions and compare the `graph-shape` funnel (passages > open > mapped > kept) and run time. |
| 13 | Venues in `triples.ttl` are strings, not `dblp:Stream` nodes | The corpus has venue strings but no DBLP stream IRIs; the provenance store only accepts subschema predicates and classes. The answer graph shows the venue as one shared node. | `harness_baseline/outcomes.py`, `harness_graphstore` | Resolve stream IRIs at ingest (DBLP `publishedInStream`), then export them. |
| 14 | The DBLP seed declares some ranges as `xsd:anyUri` | Upstream typo (the XSD datatype is `xsd:anyURI`); not an OWL 2 datatype, so a strict OWL 2 DL checker flags it. The seed file is kept unchanged. | `seed/dblp_schema_2024-06-14.ttl` | Correct it in the merged graph if a strict OWL 2 profile check is added. |
